## Authorized outcome

An eligible Lead receives one truthful, model-free acknowledgment when a supported Review or provider failure prevents an answer. Complaints, refund actions and customer-support actions take precedence over sales qualification. Ordinary greetings and qualification statements receive an appropriate conversational reply without creating a false knowledge Review. A real request to speak to staff is distinguished from ordinary references to sales, a person or an agent.

## Routing contract

Run the existing tenant, launch, claim and Conversation authority checks first. Within the owned attempt, classify the current public Lead request before sales qualification side effects:

| Request | Intended behavior |
|---|---|
| Complaint, refund action, payment/access dispute or actionable customer-support request | Persist the appropriate existing Review reason and one eligible fixed acknowledgment. Do not qualify, generate facts, create a sales handoff or append a qualification question. |
| General question about an approved refund policy, price or support programme | Keep the existing knowledge path and approved-source authority. An informational topic word alone must not force the transactional support route. |
| Actual request to speak to a person, in English or Swahili | Use the existing configured general human-request policy. Complaint/refund/support precedence cannot be overridden by this branch. Do not invent an assignment or force a sales handoff merely because someone asks. |
| Greeting only, language question or simple acknowledgment | Return the existing appropriate fixed reply, optionally with one relevant missing question where the existing flow allows it. Do not create a no-knowledge Review. |
| Clear qualification statement | Capture supported evidence through the existing qualification service, then acknowledge and ask only the next missing relevant question. Do not call it an unanswered business question. |
| Business question, including a greeting followed by a real question | Run existing retrieval and grounded generation. Preserve commercial authority, verification and all earlier pilot fixes. |
| Unclear statement | Use a conservative clarification without inventing evidence. Do not advance qualification by merely suppressing repeated text. |

Use the existing shared ConversationIntentClassifier/public result contract, extending it only as needed for these bounded routing decisions. Do not put overlapping request regexes in the processor and acknowledgment renderer. Preserve ordinary business questions prefixed with greetings. Match requests/actions rather than bare words such as `sales`, `person`, `agent`, `support` or `refund`; test negated, quoted and informational uses.

General human-request policy remains unchanged. Complaints/refunds/support are customer-service Review routes and must not require sales qualification first. The emergency does not authorize post-transition automated handoff confirmations.

## Review acknowledgment contract

- Eligibility is limited to supported inbound orchestration Review paths: no approved knowledge, conflicting knowledge, sensitive question/action, angry question, unverified source, stale source and provider failure. Lifecycle/control/tenant/launch/opt-out blocks never produce an acknowledgment. Unsupported-media and qualification-blocker behavior remain with their existing owners unless the combined-base review explicitly shows this slice must touch them.
- Render fixed English/Swahili templates from the routed category and question language. No model call is needed. Do not add a translation service or broaden retrieval language behavior.
- Only say a request was recorded for review after the Review exists. Do not claim an operator has been assigned, give a response deadline, approve a refund/access, quote commercial facts or expose provider errors/credentials. Complaint/refund/support acknowledgments have no appended qualification question.
- Retain the original blocked/failed state, blocked reason, provider failure class and Review association. Record acknowledgment identity/status separately in the existing decision/message metadata; do not label it a grounded answer or erase the failure to make the operation appear successful.
- Within the owning transaction, reuse the current outgoing Message and domain OutboxEvent creation boundary with the actual Review association and a stable per-inbound-intent idempotency identity. The existing unique `ai-outbound/<intent id>` key is suitable if the combined source still guarantees only one response per intent. A blocked intent may reference its acknowledgment Message without becoming completed or recoverable model work.
- Keep ProviderFailureHandler record-only where possible; the owning IntentProcessor explicitly coordinates the acknowledgment after verifying its current claim/control authority. The failure rescue path must also reach the common post-transaction enqueue step. Do not enqueue network work while holding the Conversation lock.
- Configured operator Review alerts follow the same commit-before-enqueue rule. Use the existing service enqueue options to persist alert Messages first, then let the owning processor enqueue their recorded identities after commit. A queue failure must leave both the customer acknowledgment and operator alerts recoverable through their existing R04 delivery records.
- An expired claim whose attempt budget is exhausted uses the same eligible provider-failure Review/acknowledgment path without another model attempt. Preserve `failed`, `claim_recovery_exhausted` and its attempt count. A live claim or revoked authority still produces no acknowledgment.
- Use R04 Message → OutboxEvent → WhatsApp OutboundDelivery → existing sender. Preserve claim ownership, current control/version, assignment, opt-out, launch, recipient, response-window, greeting-order and later human-activity checks. Queue failure must be recoverable through R04; uncertain provider acceptance must never trigger blind resend.
- Never add a global HumanReviewRequest callback for customer acknowledgments. Delivery-unknown Reviews, operator alerts, private reviews and unrelated Review creators must not create a recursive acknowledgment or extra Lead message.
- A handoff/takeover can invalidate queued automation. Do not bypass that by impersonating a User, changing observed versions or weakening sender eligibility. A genuine post-transition handoff notice is held for a separate authority decision.

## Test-first sequence

Implement one vertical behavior at a time: write one meaningful failing public-seam regression, record its red result, make the smallest correction, then keep that behavior green before the next slice.

1. **Complaint precedence:** English complaint asking for a human must produce Review plus one eligible acknowledgment, with no qualification prompt or sales handoff. Add the Swahili counterpart and a refund/support action. Pair each with informational-policy/support questions that retain approved knowledge behavior.
2. **Review acknowledgment:** a source conflict or missing price has its original Review/reason plus one fixed acknowledgment, with no substantive answer. Repeating the same job creates no additional Review, Message or outbox event.
3. **Provider failure acknowledgment:** actual adapter HTTP 402 creates the correct failure metadata/Review and one fixed acknowledgment. Then cover timeout, invalid JSON, safety refusal and `finish_reason: length`. Adapter truncation rejection remains unchanged; provider content must never leak into the acknowledgment.
4. **Human-request precision:** an English/Swahili staff request follows the configured policy; ordinary sales help, quoted/negated requests and mentions of an agent do not take the staff-request branch. Complaint precedence remains stronger than this branch.
5. **Ordinary conversation:** greeting-only and language questions do not create Reviews. A greeting-prefixed business question still reaches retrieval. A supported business statement persists evidence and asks a different missing question; coordinate the parser dependency with R09 and never fake its result. Two-turn corrections preserve provenance and do not repeat already answered questions.
6. **Authority and delivery:** takeover or lost model ownership suppresses acknowledgment creation; takeover/assignment/opt-out/gate withdrawal/window expiry after recording cancels delivery. Competing jobs/claims, queue failure/recovery and uncertain acknowledgment acceptance preserve one logical message and no blind resend. Creating a delivery-unknown Review cannot create another acknowledgment.
7. **Combine and retain:** run the scoped integration selection below and R09's evidence cases against the exact combined source. Review the final diff independently, record exact source and checks, then commit with normal hooks. The coordinator alone integrates and deploys.
