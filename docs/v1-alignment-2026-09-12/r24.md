## What to build

A client can buy extra usage or upgrade mid-month and see the exact resulting balance before paying.

Implement one complete owned Rails/Vue path across storage, permissions, API, jobs/provider and UI. Follow the approved 12 September product agreement and ADR 0016. Preserve MIT, tenant isolation, consent, canonical delivery and current evidence.

## Acceptance criteria

- [ ] Preview configured top-up cost/units or plan-price difference with same-cycle renewal date, previous usage and resulting allowance. Reject ambiguous currency/plan transitions rather than guessing.
- [ ] Manual platform payment confirmation activates the requested purchase exactly once, with immutable actor/reference/amount/currency/purpose. A later payment gateway can call the same verified entitlement boundary; no online provider integration is included now.
- [ ] Use included allowance first. Purchased top-ups carry forward while subscription active and are not erased on renewal. Expired subscription stops AI use while preserving recorded extras; reactivation policy is explicit in UI and tests.
- [ ] Upgrade charges higher plan price minus current plan price for the cycle, replaces total included allowance, preserves already consumed units and extras, and does not move renewal. Example 1000 to 3000 after 800 used leaves 2200 included units.
- [ ] Configured top-ups are more expensive per unit than included usage in the applicable higher plan; show honest computed savings, never an unverified fixed 20% claim. No automatic charges/top-ups.
- [ ] Test duplicate payment, concurrent usage/upgrade/renewal, failed confirmation rollback, multiple upgrades, carried balances and access isolation. Downgrades/refunds/disputes route to manual review. Phone and desktop flows remain plain language.
